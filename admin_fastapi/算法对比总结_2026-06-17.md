## 1. 总体结论

当前链路已经基本通畅，FastAPI 能正常调用 `http://43.139.178.169:8001/api` 下的新算法接口。

最新日志显示，体温单位问题已经修正，接口入参已按新算法要求发送 `摄氏度 * 100`，例如 `3639`、`3645`，新算法返回 `bodyTemperature=36.3/36.4`，已经不是之前异常的 `0.4`。

当前剩余差异主要来自三类原因：

1. 新旧算法的评分语义不同。
2. 睡眠期间 HRV 数据缺失。
3. 活动模块把“风险分”当作“正向活动分”使用，导致未达标时也可能显示满分。

其中活动满分问题最明确：新算法的 `/physicalHealth/activityRisk` 返回的是风险分 `riskScore`，不是活动分。日志中 2026-06-17 步数只有 5476，但 `activityRisk.riskScore=0`，如果后端做 `100 - riskScore`，前端就会显示活动 100 分。这和旧 Java 的活动评分逻辑不一致。

## 3. 旧 Java 后端算法特点

旧 Java 后端不是调用 `api.qkeering.com` 的健康算法接口，而是在本地用规则公式计算健康分。

### 3.1 身心平衡综合分

旧 Java 在 `DataServiceImpl` 中分别计算：

- 心率分
- 血氧分
- 体温分
- HRV 分
- 压力/放松分
- 活动分
- 睡眠分

最后再组合为总体健康分。

这种方式的特点是：

- 规则固定，可解释性强。
- 对接口数据窗口依赖较少。
- 当 HRV 缺失时，部分分项可以跳过，不一定严重拉低总分。
- 更像“当天健康数据规则评分”。

### 3.2 睡眠旧算法

旧 Java 睡眠评分使用：

- 总睡眠时长，理想值 480 分钟。
- 深睡比例，目标 18%。
- 浅睡比例，目标 55%。
- REM 比例，目标 22%。
- 清醒时间和睡眠效率。

它不强依赖睡眠期间 HRV。

因此在同样是 6 小时多睡眠的情况下，旧 Java 可能给出相对稳定的 60 多分；新算法如果发现睡眠 HRV 缺失、睡眠分期或活动状态异常，就可能给出更低分。

### 3.3 体征旧算法

旧 Java 体征分由有效项平均得到：

- 心率分
- 血氧分
- 体温分
- HRV 分

如果某项没有有效值，旧 Java 会忽略该项，不参与平均。

这会让旧算法在数据缺失时更“宽容”。新算法更强调输入完整度和时间序列质量，所以同一组数据在新算法中可能分数更低，但解释性更依赖新算法返回的 details。

### 3.4 压力旧算法

旧 Java 压力分本质是“压力越低，分越高”，偏向当天压力数组的规则转换。

新算法 `/stressRatio` 返回的是压力比例、平均压力、高压力天数等指标。前端如果展示“放松状态”，需要明确转换逻辑，比如 `100 - avgStressLevel`，不能直接把 `stressRatio` 当正向分。

### 3.5 活动旧算法

旧 Java 活动分比较直接：

- 步数最高 40 分。
- 中高强度活动最高 40 分。
- 总活动时长最高 20 分。

其中步数等级包括：

- 10000 步：40 分
- 8000 步：35 分
- 6000 步：30 分
- 4000 步：20 分
- 2000 步：10 分

因此旧 Java 不会在 5000 多步、未达到目标的情况下给活动满分。

## 4. 新算法接口逐项分析

新算法来自 `openapi.json`，主要接口如下：

- `/api/physicalHealth/sleepScore`
- `/api/physicalHealth/lifestyleScore`
- `/api/physicalHealth/vitalSignsScore`
- `/api/physicalHealth/stressRatio`
- `/api/physicalHealth/ovulationPrediction`
- `/api/physicalHealth/sleepRhythm`
- `/api/physicalHealth/sleepActivation`
- `/api/physicalHealth/sedentaryRisk`
- `/api/physicalHealth/activityRisk`
- `/api/physicalHealth/exerciseRegularity`

### 4.1 sleepScore 睡眠评分

新算法要求：

- 最近 24 小时睡眠记录。
- 约 10 分钟一条。
- 字段包含 `ts`、`hrv`、`activity`、`sleepType`。
- `sleepType` 枚举：0 清醒，1 浅睡，2 深睡，3 REM。

当前日志：

- 2026-06-15：`recordCount=287`，`hrv+=0`，返回 34。
- 2026-06-16：`recordCount=228`，`hrv+=0`，返回 29。
- 2026-06-17：`recordCount=187`，`hrv+=0`，返回 51。

问题分析：

1. 记录数充足，但睡眠期间 HRV 全部为 0。
2. 新算法把 HRV 作为睡眠质量的重要因子时，HRV 缺失会直接影响评分。
3. 旧 Java 睡眠评分不依赖 HRV，所以同一段 6 小时多睡眠，旧算法可能高于新算法。
4. 如果睡眠期间硬件没有传 HRV，新算法优势无法发挥。

建议：

- 新算法返回 `hrvCoverage`，例如有效 HRV 条数 / 总睡眠条数。
- 当 HRV 覆盖率低于阈值时，启用降级评分：以时长、分期、清醒次数为主，标记低置信度。
- 前端展示睡眠分时可增加“数据不足/HRV缺失”提示，避免用户误以为身体状态很差。

### 4.2 vitalSignsScore 生命体征评分

新算法要求：

- 最近 24 小时体征时序。
- 约每小时一条。
- 字段包含 `ts`、`hr`、`spo2`、`hrv`、`temp`。
- `temp` 必须为摄氏度乘以 100，例如 36.5 摄氏度传 3650。

当前日志：

- 2026-06-15：`recordCount=24`，`hrv+=24`，`temp=[3639,3639]`，返回 79，体温 36.3。
- 2026-06-16：`recordCount=20`，`hrv+=20`，`temp=[3642,3641]`，返回 79，体温 36.4。
- 2026-06-17：`recordCount=16`，`hrv+=16`，`temp=[3645,3645]`，返回 79，体温 36.4。

问题分析：

1. 体温单位已经修复。
2. 体征多点数据已经传入，不再是单条。
3. 当前体征分 79，基本合理。
4. 旧 Java 是有效项平均，新算法是算法服务综合评分，结果可能不同，但当前没有明显异常。

建议：

- 保留当前温度转换逻辑。
- 日志继续记录 `temp` 原始值和发送值，避免后续设备端单位变化再次引入 0.4 摄氏度问题。
- 建议新算法返回分项分：心率、血氧、体温、HRV 各自对总分的贡献。

### 4.3 stressRatio 压力比例

新算法要求：

- 最近 7 天压力时序。
- 约每小时一条。
- 字段包含 `ts`、`stress`。

当前日志：

- 2026-06-15：`avgStressLevel=41.6`，`stressRatio=88.89`。
- 2026-06-16：`avgStressLevel=41.9`，`stressRatio=91.67`。
- 2026-06-17：`avgStressLevel=41.2`，`stressRatio=88.1`。

问题分析：

1. 新算法返回的是压力水平和比例，不是直接的“放松分”。
2. 如果前端要展示“放松状态”，需要把压力值转换成正向分。
3. 旧 Java 的压力分更像 `压力越低分越高`，语义更接近前端“放松状态”。

建议：

- 明确前端字段语义：`stressRatio` 不直接等于放松分。
- 后端可以统一输出 `relaxScore = 100 - avgStressLevel`，但需要命名清楚。
- 新算法最好直接提供正向 `relaxScore`，避免各端自行转换。

### 4.4 activityRisk 活动风险

新算法要求：

- 最近 7 天活动时序。
- 约每小时一条。
- 字段包含 `ts`、`steps`、`activity`。

当前日志：

- 2026-06-15：`steps=6337`，`riskScore=0`。
- 2026-06-16：`steps=2874`，`riskScore=30`。
- 2026-06-17：`steps=5476`，`riskScore=0`。

问题分析：

1. `activityRisk` 是风险分，分数越高代表风险越高。
2. 旧 Java 的 `activityScore` 是正向分，分数越高代表活动越好。
3. 如果后端使用 `100 - riskScore` 作为活动分，会导致 5476 步得到 100 分。
4. 这正是当前“活动目标没达成但活动 100 分”的根因。

建议：

- 不要把 `activityRisk.riskScore` 反向作为活动分。
- `activityRisk` 只用于风险提示，例如“活动不足风险低/中/高”。
- 如果健康页需要当天活动分，应让新算法提供专门的正向 `activityScore`。
- 如果必须临时映射，建议优先使用旧产品目标口径，例如 8000 步目标，但这会变成后端本地规则，不再是纯新算法。

### 4.5 exerciseRegularity 运动规律性

新算法要求：

- 最近至少 4 周。
- 约每小时一条。
- 字段包含 `ts`、`steps`、`activity`。

当前日志：

- 2026-06-15：`regularityScore=15`，`avgWeeklyFrequency=1.8`。
- 2026-06-16：`regularityScore=15`，`avgWeeklyFrequency=1.8`。
- 2026-06-17：`regularityScore=28`，`avgWeeklyFrequency=2`。

问题分析：

1. 当前规律性分数偏低，说明过去 4 周运动规律不够。
2. 它适合表达“长期运动规律”，不适合单独表达“今天活动是否达标”。
3. 之前日志里存在非常大的步数，例如 `157729`，这类异常历史点可能影响规律性分析。

建议：

- 对历史步数做异常过滤，避免极端值影响 4 周规律判断。
- 新算法最好区分“当天活动达标分”和“长期规律性分”。
- 健康首页如果只显示一个活动分，应优先使用“当天达标分”；规律性放在详情解释中。

### 4.6 lifestyleScore 生活方式评分

新算法要求：

- 最近 30 天。
- 每天一条。
- 字段包含 `ts`、`steps`、`sleepType`。

当前日志：

- 2026-06-15：40。
- 2026-06-16：40。
- 2026-06-17：24。

问题分析：

1. 生活方式分数偏低，和长期步数、睡眠节律有关。
2. 它不是当天活动分，也不是当天睡眠分。
3. 如果把它直接放进首页身心平衡，会导致当天状态和长期生活方式混在一起。

建议：

- 首页身心平衡可以引用，但不建议完全替代当天活动/睡眠。
- 详情页适合展示生活方式趋势。
- 新算法返回应增加扣分原因，例如睡眠不规律、步数不足、数据缺失。

### 4.7 sleepRhythm 睡眠节律

新算法要求：

- 最近至少 7 天。
- 至少 3 天有完整入睡/起床。
- 字段包含 `ts`、`sleepType`。

当前日志：

- 2026-06-15：`avgSleepDuration=8.1`，`rhythmStability=较差`。
- 2026-06-16：`avgSleepDuration=7.5`，`rhythmStability=较差`。
- 2026-06-17：`avgSleepDuration=7.2`，`rhythmStability=较差`。

问题分析：

1. 现在已经不再是单天数据，接口能返回节律结果。
2. 当前节律稳定性较差，说明入睡/起床时间波动较大。
3. 这个接口适合做趋势说明，不适合直接等同于当天睡眠评分。

建议：

- 作为睡眠详情解释项使用。
- 新算法可以输出数据是否足够、有效天数、缺失天数。

### 4.8 sleepActivation 睡眠激活

新算法要求：

- 最近 24 小时。
- 约 10 分钟一条。
- 字段包含 `ts`、`activity`、`sleepType`。

当前日志：

- 2026-06-15：activation=39.6。
- 2026-06-16：activation=36.9。
- 2026-06-17：activation=35.1。

问题分析：

1. 激活度处于中等。
2. 它描述睡眠/活动状态活跃度，不是睡眠主评分。
3. 如果睡眠分低而激活度中等，需要结合 HRV 缺失、分期比例解释。

建议：

- 放在睡眠详情页作为辅助指标。
- 不建议单独进入首页总分权重。

### 4.9 sedentaryRisk 久坐风险

新算法要求：

- 最近 1 天。
- 约每小时一条。
- 字段包含 `ts`、`steps`、`activity`。

当前日志：

- 2026-06-15：riskScore=100。
- 2026-06-16：riskScore=100。
- 2026-06-17：riskScore=100。

问题分析：

1. 久坐风险高，说明小时级活动分布存在长时间不活动。
2. 这可以和 `activityRisk` 同时存在：一个人当天步数不低，但仍然可能久坐风险高。
3. 它不能当作活动分，只能作为风险提示。

建议：

- 前端展示为“久坐风险”，不要混入活动达标分。
- 新算法应返回最大连续久坐时长、久坐小时数等解释字段。

### 4.10 ovulationPrediction 排卵预测

新算法要求：

- 最近 2 个月每日数据。
- 字段包含 `ts`、`temp`、`hr`，以及经期开始日期、周期长度。
- `temp` 同样要求摄氏度乘以 100。

当前健康首页主要问题暂未集中在该接口。

建议：

- 继续复用已修复的体温单位转换。
- 如果前端开启女性健康相关能力，需要保证 2 个月历史数据和周期参数齐全。

## 5. 同一组数据下新旧算法分数差异的根因

### 5.1 睡眠差异

旧 Java：

- 看时长和阶段比例。
- 不强依赖 HRV。
- 数据缺失时更宽容。

新算法：

- 看睡眠序列、HRV、活动、分期。
- 当前睡眠 HRV 全为 0。
- 所以 6 小时多睡眠不一定比另一晚得分高。

根因：

- 硬件在睡眠期间没有提供有效 HRV。
- 新算法的评分因子比旧算法更多。
- 新算法缺少对 HRV 缺失的明确降级说明。

### 5.2 体征差异

旧 Java：

- 有效项平均。
- 数据缺项时忽略。

新算法：

- 24 小时多点时序评分。
- 对体温单位敏感。

根因：

- 之前体温单位错误导致体温被算成 0.4 摄氏度。
- 当前已修复，体征分恢复到 79 左右。

### 5.3 压力差异

旧 Java：

- 输出正向压力健康分。

新算法：

- 输出压力比例和平均压力。

根因：

- 字段语义不同。
- 前端展示“放松状态”时必须统一转换为正向分。

### 5.4 活动差异

旧 Java：

- 活动分是正向分。
- 8000 步左右才接近较高分。
- 5000 多步不会满分。

新算法：

- `activityRisk` 是风险分。
- `riskScore=0` 代表风险低，不代表活动满分。
- `exerciseRegularity` 是长期规律分。
- `lifestyleScore` 是生活方式分。

根因：

- 风险分和活动分混用。
- 新算法没有直接提供首页需要的“当天活动达标正向分”。

## 6. 推荐调整方案

### 6.1 后端展示层调整

活动模块不要再使用：

```text
activityScore = 100 - activityRisk.riskScore
```

建议改为以下方案之一：

方案 A：要求新算法提供正向 `activityScore`。这是最干净的方案。

方案 B：短期内首页活动分使用 `lifestyleScore` 或 `exerciseRegularity`，但文案要改成“生活方式/运动规律”，不要叫“今日活动分”。

方案 C：短期内后端按旧产品目标口径计算今日活动达标分，但这会重新引入本地规则，不是纯新算法。

### 6.2 新算法接口建议

建议算法侧新增或调整：

- `activityScore`：正向当天活动达标分。
- `relaxScore`：正向放松分。
- `sleepDataQuality`：睡眠 HRV 覆盖率、有效睡眠条数、睡眠分期分布。
- `vitalDataQuality`：体温单位检测、有效体征条数、各分项分。
- `insufficientDataReason`：数据不足时明确返回原因。

### 6.3 数据质量日志建议

后端日志已经记录了请求和响应，建议继续保留，并增加摘要字段：

- `recordCount`
- `dedupeCount`
- `hrvValidCount`
- `tempMin/tempMax`
- `stepsMax`
- `sleepTypeDistribution`
- `windowDays`

这样后续再出现分数异常时，可以直接判断是算法问题、数据问题，还是展示映射问题。

## 7. 当前问题优先级

P0：

1. 活动分不要再用 `100 - activityRisk.riskScore`。
2. 睡眠 HRV 缺失需要在算法或展示层做降级说明。

P1：

1. 运动规律接口过滤极端步数，例如 157729 这类异常值。
2. 压力接口统一输出正向放松分。
3. 新算法返回更多分项和数据质量信息。

P2：

1. 生活方式、睡眠节律、久坐风险从首页主分拆成详情解释项。
2. 前端展示文案区分“分数”和“风险”。

## 8. 最终判断

当前不是简单的新算法“算错”，而是新算法接口的指标语义更细，和旧 Java 首页四项分的语义没有一一对应。

旧 Java 的四项分是：

- 睡眠分
- 体征分
- 放松分
- 活动分

新算法对应的是：

- 睡眠质量
- 体征质量
- 压力比例
- 活动风险
- 久坐风险
- 运动规律
- 生活方式
- 睡眠节律
- 睡眠激活

其中只有睡眠、体征可以比较直接映射；压力需要转换；活动不能直接用风险分反推。

因此建议下一步先修正活动分映射，再要求算法侧补充正向 `activityScore` 和数据质量字段。这样既能继续坚持“按新算法走”，又不会让前端出现 5000 多步却活动 100 分这类明显不合理结果。
