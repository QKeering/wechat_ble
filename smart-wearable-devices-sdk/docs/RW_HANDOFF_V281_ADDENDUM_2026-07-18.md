## Frontend changes

- `src/sdk/ring-ble/rw/protocol.ts` now includes `Activity`, `Sleep`, and `ActivityCurrentDay` as RW health data keys.
- `src/sdk/ring-ble/rw/history.ts` now adds `activity-current-day`, `activity-history`, and `sleep-history` to AB history fallback. Default fallback includes `step` and `sleep`.
- `src/sdk/ring-ble/rw/parser.ts` now converts activity payloads into `stepCount/step` records and sleep payloads into backend-compatible `sleepState/durationMinutes` records.
- `src/sdk/ring-ble/rw/parser.ts` also accepts 1x, 10x, and 100x temperature units for RW `0x0508` history records.
- Mine-page core protocol probe is now narrowed to the current gap: `history-key/activity-current-day/read` (`0x051A`), `history-key/activity/read` (`0x0502`), `history-key/sleep/read` (`0x0505`), and temperature checks. The long realtime control/read probes remain in full mode only.
- Mine compact logs now expose `stepCount`, `sleepState`, `sleepStatus`, and `durationMinutes`, so the next pasted log can show whether parsing reached the page.
- Home-page RW history upload now emits `history-page-upload-start` before posting to `/app/data/sync`, including `submitRecordCount`, `submitMetricCounts`, and `submitRecordSample`. Upload failures are logged with the same context and use silent request config so background sync does not interrupt the business page with network toasts.
- v276 extends the `/app/data/sync` background request timeout to 90 seconds because earlier device reads could consume a large part of the default request window before upload started.
- v278 copies backend submit response fields into Mine logs: `inputCount`, `count`, `healthCount`, `sleepCount`, `failCount`, `elapsedMs`, `syncElapsedMs`, `healthWriteMs`, `sleepWriteMs`, `deviceUpdateMs`, `summaryMs`, `touchedDates`, and `summaryDates`.
- v278 also logs `uploadTimeoutMs=90000` separately from the device read `timeoutMs`, so upload timeout and BLE read timeout are not confused.
- Device history read results now report `deviceUploaded` and `backendUploadPending` instead of reusing the ambiguous `uploaded` name. Backend submit attempts report `backendUploadStarted`, `backendUploaded`, `backendSubmitted`, and `rawError` on failure.
- v291 adds `primarySubmitMetricCounts` to history-page logs and uses it for fallback decisions. Missing step/sleep fallback now runs before missing vital fallback, and fallback result logs include both `rawMetricCounts` and `submitMetricCounts`.
- v291 filters zero-step placeholders and zero-minute sleep placeholders out of the useful-history path. A database row with default `step_count=0` or `sleep_state=0` should no longer be mistaken for a successful RW step/sleep sync.
- v296 fixes the SY03 `0x0505` sleep parser using the RW APP SDK JL format. The payload is 7-byte records: big-endian seconds since 2000, one JL sleep model byte, and two reserved bytes. The parser now emits sleep segments with `startTimestamp`, `endTimestamp`, `durationMinutes`, and L19-compatible `sleepState`, and it prevents the old scalar fallback from uploading `0x2e` as `sleepState=46`.
- Detail-page backend query failures now also include `rawError`, so inner-page timeouts can be distinguished from BLE command timeouts without digging through vConsole.
- Homepage auxiliary requests for dictionaries and girl-health cards now use silent request config and log `business-aux-request-failed` instead of showing a toast or stopping RW history sync.
- Network request timeouts now remain classified as network failures in logs and toasts; they are no longer mislabeled as BLE command no-response failures.
- Empty ACK and zero-step records are not uploaded as useful history records.
- One tag-273 log showed `records=2` for step/sleep sync, and the tag-275 log showed `records=3` for heart rate and blood oxygen. v278 is now meant to prove whether those records are submitted to `admin_fastapi` and inserted into `health_raw`/`sleep_record`.
- `historyStartDate` and the original `sinceTimestamp` filter remain in place, so fallback reads can be broad while upload still avoids old bulk backfill.

## Backend changes

- `admin_fastapi` `/app/data/sync` now includes `inputCount`, `elapsedMs`, `syncElapsedMs`, `healthWriteMs`, `sleepWriteMs`, `deviceUpdateMs`, `summaryMs`, and `summaryDates` in the response.
- The same endpoint writes a `data_sync` algorithm log entry with `input_count`, `elapsed_ms`, `count`, `health_count`, `sleep_count`, `fail_count`, `touched_dates`, and the same stage timing fields.
- App-layer `daily_summary` now delegates to `health.daily_summary`, which first reads `health_daily_summary` and only calculates when no summary row exists. This avoids forcing daily summary recalculation on every detail-page request.
- Post-v281 backend follow-up: `/app/data/sync` writes `health_raw`/`sleep_record` first and returns without waiting for daily summary calculation. Touched dates are scheduled through a FastAPI background task and logged as `data_sync_summary`. The response now exposes `summarySkipped=true` and `summaryScheduled=true` when summaries were queued.
- Post-v281 backend follow-up: `health_index`, `data/vitalSign`, `data/balanceScore`, `data/stress/stressDetail`, `data/motion/motionSummary`, `data/sleep/sleepOverview`, and matching family overview APIs now use local summary/raw data first instead of synchronously calling the external algorithm service. This is intended to stop business pages from timing out while still showing stored RW data.
- Post-v288 backend follow-up: `/app/data/sync` now recalculates daily summaries inline when the upload touches at most 3 dates. The response should show `summaryInline=true`, `summaryScheduled=false`, and `summarySkipped=false` for these small home-page syncs. Larger backfills still use the background task to avoid request timeout.
- Post-v288 backend follow-up: sleep detail APIs now fall back to `health_raw.sleep_state` when `sleep_record` has no segment rows. `sleepDetail` can produce a chart from raw sleep-state samples, and `sleepSegment`/`sleepSummary` can derive start/end/bed-time from raw samples. This does not fix missing bottom-layer sleep data; it only prevents pages from staying empty when RW uploads raw sleep states instead of duration segments.
- Post-v290 backend follow-up: motion APIs now fall back to `health_raw.step_count` when `health_daily_summary.total_steps` is missing or still zero. This covers the real-device case where `/app/data/sync` has inserted step rows but the summary row has not caught up yet. Affected endpoints: `/app/data/motion/motionOverview`, `/app/data/motion/motionDetail`, `/app/data/motion/motionSummary`, and `/app/family/data/motion/motionOverview`.
- Post-v290 backend follow-up: vital-sign overview APIs now fall back to `health_raw` averages/min/max when `health_daily_summary` is missing or still zero. This covers the real-device case where HRV, heart rate, SPO2, temperature, stress, glucose, or blood-pressure rows are already stored but the overview card still showed `0` because it only read summary fields. Affected endpoints: `/app/data/vitalSign` and `/app/family/data/vitalSign`.
- Backend validation: use the project virtualenv, not the system Python. Verified with `.venv/Scripts/python.exe -m unittest tests.test_rw_sleep_raw_fallback tests.test_sleepfm_export` and `.venv/Scripts/python.exe -m py_compile app/api/app.py tests/test_rw_sleep_raw_fallback.py`.
- If the phone still reports `request:fail net::ERR_CONNECTION_TIMED_OUT` and no `data_sync`/`data_sync_summary` line appears in `admin_fastapi/logs/algorithm_calls.log`, the request likely did not reach the deployed backend or the deployed backend is not the updated `admin_fastapi` instance.
