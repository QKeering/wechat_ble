# 戒指 BLE 同步链路简化方案（代码 + 运行路径视角）

> 目标：把当前"多层状态机 + 10+ 个 skip 闸门 + 上传死锁"的复杂同步，收敛为一条线性流水线：
> **连接建立通信 → 更新设备时间 → 读取电量 → 读出历史数据 → 上传后台 → 显示数据**。
> 本文只做方案设计，不修改业务代码。所有行号基于 `smart-wearable-devices-sdk/src/` 当前工作区版本。

---

## 一、当前真实运行路径（legacy 设备，D7/6E/B7 均走此路径）

用户设备 90% 是 legacy 协议（D7=B0:05:F0:00:05:D7、6E=82:C5:8D:B2:69:6E、B7=B0:05:F0:02:0B:B7），
RW 协议仅 `useRingBusinessController.ts` 内大量分支，legacy 主路径在 `pages/awareness/awareness.vue`。

### 1.1 入口触发点（谁会启动同步）
| 触发源 | 文件:行 | 调用 |

| 下拉刷新 | awareness.vue:9027 | `syncRwHomeHistoryAndRefreshOverview(..., 'pull-down-refresh', {force:true})` |

### 1.2 主编排 `executeCommandsSequentially`（awareness.vue:8523）
实际串起 legacy 流水线的是这一函数：
1. **ensure-ready**：:8574 `canUseReadyFastPath ? true : await ensureCommunicationReady()`（连接建立通信）
2. **device-info（电量闸门）**：:8616-8676 判断 `shouldReadDeviceInfoBeforeHistory`（legacy 默认 **跳** device-info，见 :8670 `skipDeviceInfoBeforeHistory:!isRwRing`）；RW 才走 `battery-not-ready-before-history` 重试链
3. **历史读**：:8686 `startLegacyHomeHistoryReadInBackground('legacy-home-sync-device-info-ready', protocol)`
4. 函数在这里就 `return` 了 —— **它自己并不读数据、不上传**，只是"派发"历史读

### 1.3 历史读 `startLegacyHomeHistoryReadInBackground`（awareness.vue:7337）
入口就有一串 **skip 闸门**（这是复杂度的核心来源）：
- :7361 cooldown skip
- :7365 缺 MAC skip
- :7382 planner `decideDeviceSync` skip（device-sync-planner）
- :7417 预检 skip（`sync-context-or-communication-not-ready` ← B7 "数据没上来"真因）
- :7439 已在读 skip
- :7455 上传中 skip（`history-upload-pipeline-active`）
- :7472 互斥 skip（`history-exclusive-active`）
- :7488 近期已完成 skip
- :7515 近期已取待上传 skip
- :7546 近期失败 skip

穿过所有闸门后真正读，读完成触发上传 watcher。

### 1.4 上传 watcher（awareness.vue 4300-5260）
- `buildLegacyLocalDataUploadBatch`（:1644）按 `uploadSinceTimestamp`（游标）过滤 → **`legacy-local-data-window-skip` reason=`before-upload-since`**（:1658）
- 分批 `submitData`（:4569），软超时 `withAwarenessSoftTimeout`（:4565）
- 成功：:4738 `markUploadedRingHistorySubmitRecordsForDevice` + :4861 推进 `checkpointTimestamp`（游标）
- 失败：:4657 抛错 → 重试，但**重试入口同样被 `before-upload-since` 挡死**

### 1.5 会话锁
- `claimAwarenessHomeSyncSession`（:673）→ `claimDeviceSyncSession`（:690，cooldown/staleMs=2min）
- 释放只在 `markAwarenessHomeSyncCompleted`（:603，被上传**成功**分支调用）
- 失败分支调 `releaseAwarenessHomeSyncSession(...,'failed',false)`（:8603/8613/7425）——但**不写 cooldown**，靠 staleMs 兜底

## 二、为什么"慢 / 数据上不来 / 反复"——根因（已用 rw-debug 日志验证）

| 现象 | 真因 | 代码位置 | 日志证据 |
|---|---|---|---|
| 永不超时 / 卡 120s | 用户新部署"keep-in-flight 不超时"改动：`LEGACY_LOCAL_DATA_SUBMIT_WATCHDOG_MS` 方向反了，HTTP 石沉大海挂 120s 才 fail（之前 5s/37s） | awareness.vue:322 + :4599 `preserve-snapshot-for-http-only-retry` | `upload-http-batch-soft-timeout` elapsedMs=119838 |
| 上传彻底停摆 | fail 后游标 `since` 不推进 → 重试被 `before-upload-since` window-skip 永久压死，闭环死锁 | :1658 / :4613 | 全天 `upload-result` 成功=0，window-skip 每 6-7s 一次到日志末尾 |
| 单飞会话永不释放 | 失败分支不写 `home-sync-cooldown` → 后续 sync 命中 `isAwarenessHomeSyncInCooldown` 被吞（`home-sync-session-released`=0） | :585-602 / :8603 | released=0，claimed/skipped 全 0（旧包）或 1 次 |
| 回导航页卡 2s | `waitForAwarenessAuxiliaryIdleSlot`（:5775）顶满 `AWARENESS_AUXILIARY_SYNC_IDLE_MAX_WAIT_MS=2000`；`homeDetailNavigating` 卡死（:2803 设 true 后无回调永不复位） | :5775 / :2792-2804 | `business-aux-request-idle-slot` waitedMs 中位 2001ms；navigation-lock 77 次 |
| 数据没上来（B7） | 导航拆 BLE 监听 → 预检 `sync-context-or-communication-not-ready` skip（:7429） | :7426 / :1252 clearDataListener | history-read-skip 53 次 |
| 电量读"很久" | 实际读取 14ms；慢在状态机空转（battery 闸门 + 重试链），非读取慢 | useRingBusinessController.ts:1261 校时 / device-info 重试 | device-info-refresh-start→ready 14ms |
| 重复历史读 | 旧包 page-show 反复触发 + 20min recent-success 门间隙放行 | :8955 / :7348 decideDeviceSync | 06:54 三次 history-read-start 同 since |

**结论**：逻辑本身"能解"，但被 **10+ 个互相咬合的 skip 闸门 + 失败分支无兜底收尾 + keep-in-flight 超时方向反了** 三重叠加，导致一条本应线性的流水线在任意异常点都会"挂死不可逆"。

## 三、简化目标架构：一条线性流水线

把"首页状态机 + 多 entry + 多 watcher"收敛为一个**单一编排器** `runRingSyncPipeline()`，
所有触发源只调用它（带 `force` 参数），内部按顺序执行、每步可独立失败重试、全程单 flight、异常必收尾。

```
                 ┌─────────────────────────────────────────────┐
   任意触发源 ──▶ │  runRingSyncPipeline(trigger, {force})        │
 (onShow/重连/   │   ① 单飞锁 claimDeviceSyncSession             │
  下拉/恢复)     │   ② if 已在跑 → 直接 return（不排队不重派）    │
                 └───────────────┬─────────────────────────────┘
                                 │
            ┌────────────────────┼────────────────────────────┐
            ▼                    ▼                            ▼
     ② 连接/通信就绪      ③ 更新设备时间              ④ 读取电量
  ensureCommunication    syncRwDeviceTimeBeforeHistory   refreshDeviceInfo
   (已连则快路径)         (同日去重 10min 跳过)          (legacy 已有缓存则跳过)
            │                    │                            │
            └────────────────────┼────────────────────────────┘
                                 ▼
                      ⑤ 读出历史数据
                 startLegacyHomeHistoryRead
                 （游标 since 只读增量；
                  读解析完即标记"已读"状态，
                  不再等上传去释放 inFlight）
                                 │
                                 ▼
                      ⑥ 上传后台（关键重做）
                 uploadBatch() 带【硬超时 30s】
                   ├─ 成功 → 推进游标 + markUploaded + 释放锁(completed)
                   └─ 失败/超时 → 仍推进到"已收到最大时间戳"
                                  + 释放锁(failed)
                                  + 调度后台补偿重试（豁免 before-upload-since）
                                 │
                                 ▼
                      ⑦ 显示数据
                 refreshPageDataAndCharts()
                 （已读即渲染，不等上传）
```

### 3.1 关键简化点（对照当前痛点）

| 当前 | 简化后 |
|---|---|
| 7+ 触发源各自编排、各自 claim | **单一 `runRingSyncPipeline`**，所有触发源只调它 |
| 10+ 个 `legacy-home-history-read-skip` 闸门 | 折叠为 3 个：**已在跑 / 通信未就绪 / 当日已传完**（planner 仅做"今天传过没"判断） |
| `executeCommandsSequentially` 派发后立刻 return，读/传在别处异步 | 流水线**同步串起**读→传→显，单函数内 await 到底 |
| `before-upload-since` window-skip 死锁 | 游标推进与"是否上传成功"解耦：**只要本地收到就推进**，上传失败只影响"后台是否拿到"，不影响下一步 |
| keep-in-flight 120s 挂死 | 上传加 **30s 硬超时**，超时即判失败走兜底 |
| 失败分支不释放锁 → cooldown 吞后续 | **任何出口（成功/失败/超时/onHide）都调 `finishDeviceSyncSession`** |
| `homeDetailNavigating` 卡死 | 导航用 `setTimeout` 兜底复位（无论 navigateTo 有无回调） |
| `waitForAwarenessAuxiliaryIdleSlot` 顶 2000ms | 辅助数据改"缓存先渲染 + 同步后兜底刷"，不再阻塞主流程 2s |
| 电量闸门空转 / 重复读 | device-info 本地缓存复用（跳过 battery 门槛），同日只刷一次 |

### 3.2 必须保留的 4 处"收尾兜底"（P0，直接决定能否彻底解决）

1. **上传 30s 硬超时**：`LEGACY_LOCAL_DATA_SUBMIT_WATCHDOG_MS` 改为 30s，且超时后**强制结束**上传 Promise，不让 HTTP 悬空。
2. **游标与上传成功解耦**：`fail/超时` 后按 `max(received)` 兜底推进 `since`；后台补偿重试**豁免** `before-upload-since` 过滤。
3. **任何出口都 release 锁**：成功→`markAwarenessHomeSyncCompleted`；失败/超时/onHide→`releaseAwarenessHomeSyncSession(...,'failed',false)`。
4. **`homeDetailNavigating` setTimeout 兜底复位**（如 1500ms 强制 false）+ `waitForAwarenessAuxiliaryIdleSlot` 上限降到 300~500ms。

## 四、落地步骤（建议顺序）

1. **抽 `runRingSyncPipeline`**：把 :8523 `executeCommandsSequentially` 与 :7337 `startLegacyHomeHistoryReadInBackground` 的读/传/显 合并为一个顺序函数；7 个触发源改为只调它。
2. **砍闸门**：`startLegacyHomeHistoryReadInBackground` 的 10 个 skip 折叠为 `recent-completed / comm-not-ready / already-running` 三个。
3. **重做上传收尾**（4 处 P0）：见 3.2。
4. **device-info 缓存化**：`refreshLegacyHomeDeviceInfoInBackground`（:6834）复用上次成功结果，legacy 同日只刷新一次。
5. **导航锁兜底**：`resetAwarenessNavigationState`（:1334）加 setTimeout 复位；idle-slot 上限调小。
6. **部署 + 抓 rw-debug 验证**：重点看 `upload-result` 成功 > 0、`window-skip` 归零、`home-sync-session-released` 每会话出现、回导航页无 2s 卡顿。

## 五、复杂度对比（预期收益）

| 维度 | 当前 | 简化后 |
|---|---|---|
| 同步入口 | 7+ | 1（`runRingSyncPipeline`） |
| 历史读 skip 闸门 | 10+ | 3 |
| 死锁风险点 | 3（上传/游标/锁） | 0（解耦 + 必收尾） |
| 单设备一次冷开端到端 | 2.5min+ 且常传不上 | 目标 <60s（读 30s + 传 20s + 校时 8s） |
| "用户简单心智模型"匹配度 | 低（状态机难追） | 高（线性 6 步） |
